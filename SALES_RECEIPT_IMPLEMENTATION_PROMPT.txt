Implement a one-time sales receipt printing workflow in this project. This project uses "sales," not "invoices," so adapt all model, route, table, and UI names to its existing sales architecture. First inspect the current sale creation, receipt printing, permissions, reports, and barcode scanning code. Reuse existing conventions and libraries.

Requirements:

1. Original receipt: add nullable printed_at and printed_by fields to sales. Only an authorized user can request the original receipt. In a database transaction, lock the sale, reject the request if it is already marked printed, then stamp it and create an audit event. The server must enforce this even if someone calls the URL directly. Update sales actions to show Print before printing and Already Printed afterward.

2. Reprint: use a separate, permission-protected POST endpoint. Require and validate a nonempty reason, reject cancelled sales, and require that an original print was recorded. Log every reprint without changing the original printed_at/printed_by values. Clearly label the rendered receipt "MANAGER REPRINT."

3. Permissions: define separate permissions for original receipt printing, reprinting, viewing the receipt print audit, and verifying delivery. Enforce them on server endpoints and use them to control visible UI actions. Fit role assignments into this project's existing permission system; do not overwrite administrator-configured grants when seeding.

4. Audit: create one durable log row per authorized original print or reprint, recording sale, operator, event type, reason where applicable, timestamp, IP address, and user agent. Build a permission-protected report showing sale number, total print count, event type, original/reprint operator, reason, print time, and delivery status. Include useful filters (sale number, operator, event type, date range, delivery status) and follow existing export conventions if available.

5. Receipt barcode: generate a unique, persistent delivery-verification code for each sale, including a migration/backfill for existing sales. Print its readable text and a scannable CODE128 barcode on the receipt using an existing barcode library or a suitable established package. Keep this code separate from product barcodes.

6. Delivery scanning: add a permission-protected verification page that accepts a USB scanner (text input), manual entry, and camera scanning where supported. Submit to a server endpoint that validates and normalizes the code, locks the sale, rejects missing/cancelled/already-delivered sales, and records delivered_at, delivered_by, and an audit event. Give clear success and duplicate-scan responses. Reuse existing camera-scanning libraries if present; otherwise choose a maintained library and provide a manual-input fallback.

7. Product scanning: if this project already has product barcode scanning at checkout, preserve it. Product scans must look up products; receipt delivery-code scans must verify delivery. Do not route one barcode type into the other workflow.

8. Handheld scanner duplicate prevention: apply the existing handheld barcode scanner correction to both Sale Create and Purchase Create. A hardware scanner commonly types the barcode and sends Enter, which can overlap with the input's change event and trigger duplicate lookups/additions. Ensure one physical scan causes at most one product row to be added: handle Enter/change consistently, guard each barcode while its lookup is in flight, and suppress an immediate repeat of the same code for a short cooldown (about 1.5 seconds). Apply the same duplicate guard to camera scan results. Clear/reset the input after a successful add, and allow a deliberate rescan after the cooldown so staff can add the same product again. Do not let a failed lookup permanently block future scans.

9. Browser Back after printing: after the print dialog closes, redirect to the sale-create page with `window.location.replace()` rather than normal navigation, so the receipt page is replaced in browser history and the Back arrow does not normally reopen it. Trigger the redirect from `afterprint` and retain a short timeout fallback for browsers that omit that event. Keep the server-side printed_at check authoritative: if the receipt URL is requested again by Back, refresh, or direct navigation, reject the already-printed original receipt. Also handle browsers that restore the receipt from the back-forward cache (for example, detect a persisted `pageshow` event and redirect), so a restored page cannot silently auto-open the print dialog again. Do not rely on client-side history behavior as the security control.

Add focused tests for authorization, concurrent/repeated first-print requests, reprint validation, audit rows, delivery verification, and duplicate scans. Run the relevant tests and report the results.

Important limitation: a web application cannot confirm that paper physically printed. The first-print stamp records authorization/rendering before the browser print dialog, not printer success. Keep that behavior clear in the UI and report; do not claim a physical-print guarantee. Make the smallest changes consistent with this repository, and summarize the files changed and any migration or role-seeding commands needed.
